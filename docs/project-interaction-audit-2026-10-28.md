# Research OS 项目与交互诊断

> 以下为修复前诊断。已落实的改动、验证和剩余范围见 [科研工作流修复说明](workflow-fixes-2026-10-28.md)。

日期：2026-10-28。依据当前工作区源码、已有前端静态产物、后端测试和独立内存数据库复现。没有修改应用代码或真实项目数据库；没有启动安装版进行逐屏操作，因此视觉表现与安装版实际行为仍需界面验证。

## 1. 项目定位与现状

当前实现是面向 AI/ML 研究者的本地科研记录系统。核心价值是保留“假设如何演化、实验如何支撑判断、判断来自哪里”的研究记忆。

- 前端：Next.js / React，项目总览、实验台、实验对比、假设详情、演化图谱、研究时间线、对话导入、Agent 导入和 AI 审核。
- 后端：FastAPI / SQLAlchemy / SQLite；领域服务维护不可变版本、项目内关联约束和部分导入的幂等性。
- AI：导入对话后提取事件、匹配假设、生成变更提案，人工审核后应用并保留来源。
- 桌面：Electron 外壳、本地后端进程、静态前端和更新桥接。

值得保留：Idea 身份与版本分离、证据指向具体版本、AI 提案先审核再应用、来源消息可追溯、对话中的实验描述不直接当作实验证据。这些是本产品区别于普通笔记工具的基础。

主要诊断：底层按实体和功能模块组织，上层尚未形成围绕一个研究问题持续工作的操作流程。用户必须自行在页面之间拼接“记录—整理—验证—判断—继续研究”。

## 2. 主要任务的实际断点

| 用户想完成的事 | 当前路径与断点 | 改进目标 |
| --- | --- | --- |
| 开始一个研究方向 | 创建项目后，总览将“继续研究”导向图谱；空图谱又要求返回项目创建假设 | 创建后直接进入新项目，用一个清楚的首要动作引导记录问题或材料 |
| 记录一个还不成熟的想法 | 先填写标题和完整假设正文，立即生成不可变 v1 | 支持先低成本记录，再整理成可验证假设；确认后的版本保留不可变原则 |
| 从假设安排实验 | 假设详情只能新增版本或关联已有证据，没有针对该假设安排实验的动作 | 在假设上下文创建实验计划，并区分“验证目标”和“结果证据” |
| 跟进实验直到完成 | 可以登记 planned/running，但实验详情没有编辑状态、结果、指标的常规入口 | 计划、运行、补录结果、解释结果形成连续路径 |
| 用结果更新认识 | 关联证据后，修订假设、修改状态、记录结论仍分散或没有入口 | 展示证据后允许研究者明确记录判断，再选择修订、继续验证或搁置 |
| 整理 AI 讨论 | 导入、分析、审核、应用、返回图谱跨多个模块，历史任务恢复不足 | 统一材料与待处理入口，处理后直接定位产物 |
| 回来继续研究 | 总览的“下一步”使用简化推断；图谱“下一步”始终是固定空提示 | 展示真实未解问题、实验计划和未处理结果，并可跳转或完成 |

## 3. 应优先修复的具体问题

优先级定义：P0 为核心路径或可信确认结果受到直接影响；P1 为日常任务明显受阻；P2 为可理解性、扩展性和效率问题。

### P0-01：桌面静态路由与参数校验冲突

证据：`frontend/src/app/projects/[id]/page.tsx:9` 只生成 `id="app"`，随后在服务端把非正整数参数渲染为 InvalidParamScreen。类似模式存在于实验、图谱、对话、审核等页面。`desktop/main.cjs` 将数字路径映射到这些占位 HTML。

验证：现有 `frontend/out/projects/app.html`、`out/projects/app/experiments.html`、`out/analysis/app.html` 均包含“页面地址无效或尚未就绪”。

影响：静态占位产物本身已经是无效页，文件映射不等于动态路由重新执行。应优先验证安装版直接访问、内部跳转和刷新；不能只以 Web 模式通过判断桌面可用。

### P0-02：AI 审核侧栏入口指向不存在的页面

证据：`frontend/src/components/app-sidebar.tsx:123` 将 AI 审核解析为 `/projects/{id}/analysis`，源码没有该路由，实际审核在 `/analysis/{jobId}`。

影响：一级导航无法到达承诺的功能。应有项目级待审列表，再进入具体任务。

### P0-03：会话列表与任务状态使用不同 ID

证据：`conversations-view.tsx:133,145` 使用 job.id 保存状态，`:297` 使用 conv.id 读取。

影响：任务 ID 与会话 ID 不同时，进度和进入审核按钮丢失，甚至可能展示别的会话的任务。第一次恰好同号会掩盖问题。

另外，jobs 只在本页内存维护，加载会话时不恢复历史分析任务；刷新或离开再回来后无法恢复完整任务状态。失败任务在获得 job 后也没有明确重试动作。

### P0-04：Agent 预览与正式导入结果不同

证据：`backend/app/importers/agent_import.py:230,249` 的 dry_run 分支提前 continue，没有为新假设、新实验登记可供后续条目解析的引用。

已复现：在独立内存数据库中，同一份“新假设 i1 + 新实验 r1 + 两者的支持证据”JSON，预览返回 ok=false、2 项拟创建、证据引用不存在；正式导入返回 ok=true、3 项创建。

影响：最典型的综合导入会产生错误预览。预览必须使用与正式执行一致的引用解析和校验规则。

### P0-05：确认导入不绑定预览内容

证据：`agent-import-view.tsx:190` 编辑文本只更新 content；`:152` 切换模块只更新 activeKey；`:200` 只判断 preview 是否存在即可确认。

影响：预览 A 后修改为 B，确认时实际提交 B，界面仍展示 A 的结果。应让内容、项目或模块变化使旧预览失效，提交时核对预览对应的输入。

## 4. 日常交互缺口

### P1-01：项目上下文不能覆盖详情和审核页

`project-context.tsx:61` 只识别 `/projects/{id}`；`app-sidebar.tsx:70` 切换项目也只在这类路径跳转。`/ideas/{id}`、`/runs/{id}`、`/analysis/{jobId}` 没有按实体归属同步当前项目。

影响：直接打开详情，或在详情里切换项目，侧栏可能显示 B 项目而正文仍属于 A。顶部面包屑还把这些路径的实体数字 ID 当项目 ID 使用（`topbar.tsx:107`）。

### P1-02：创建和删除项目不刷新全局项目列表

首页非空状态的 ProjectCreateDialog 回调只重新加载当前项目数据（`app/page.tsx:220`），没有 refresh 项目上下文，也不切换到新项目；删除项目后也只跳首页（`project-detail-view.tsx:96`）。

影响：新项目可能不出现在切换器中，删除后仍保留旧项目状态。应统一刷新列表、确定当前项目并导航。

### P1-03：常规维护入口不足

后端支持修改项目、假设状态、实验和笔记；前端 `updateProject`、`updateIdea` 仅定义而无调用。实验详情没有编辑状态、补录指标入口；笔记没有编辑入口。

影响：用户可以建立记录，却难以维护记录。尤其手动创建的 running 实验，无法用常规页面操作改为完成。

### P1-04：主工作区偏重浏览，缺少就地操作

图谱有搜索、布局、小地图、筛选和五个详情标签，但已有节点面板没有修订假设、安排实验、关联证据、补充笔记等动作。已有图谱也没有直接创建假设入口。

总览的“继续研究”默认进入图谱，后续真正工作却要跳到假设时间线或旧项目详情，打断上下文。

### P1-05：“下一步”没有接入真实记录

`IdeaDetailPanel.tsx:155` 始终渲染固定空提示；AI 的 open_question 已在 `backend/app/ai/proposals.py` 保存为 `Next:` 笔记，但该标签没有读取或筛选它们。

首页把最近成功/失败实验直接称为“尚未关联证据”（`app/page.tsx:114`），没有检查证据关联或复盘状态，因此建议可能与真实情况冲突。

### P1-06：审核界面无法完成自己要求的人工修正

提案卡片要求人工确认目标假设，但编辑对话框只提供标题、正文、变更原因（`review-view.tsx:490`），没有目标假设、关系端点或状态选择。后端虽然允许 target_idea_id、relation、status，界面没有提供。

保存按钮要求非空标题；关系、状态类提案通常没有 title，用户不能直接保存针对这些动作的合理修改。提案依赖也未在卡片中解释，接受下游、拒绝上游后只能等应用时才看到拦截。

### P1-07：变更预览并不是将被应用结果的可靠模拟

`ProposalGraphPreview.tsx` 不按 accepted 状态筛选提案，只绘制新增假设和部分边，没有模拟新增版本、状态变更；对象形式的提案引用被直接 String 化，也没有完整解析到新节点。

影响：Before / After 名称容易让人认为这就是应用后的图，实际只是不完整的提案叠加。需要模拟一致的变更集，或明确降低预览承诺。

### P1-08：历史待审事项没有完整入口

`backend/app/analysis.py:678` 跨任务累计 pending_count，却返回最新完成任务的 latest_job_id。首页和图谱拿累计待审数链接到这一个任务。

影响：旧任务还有待审，最新任务已经处理完时，点击待审仍进入最新任务，无法看到完整队列。

### P1-09：来源定位承诺未实现

`IdeaDetailPanel.tsx` 生成 `/analysis/{jobId}?msg={messageId}` 并承诺定位原消息，但审核页没有读取 msg 参数。卡片来源还显示数据库消息 ID，左侧显示会话内 sequence，两套编号不一致。

## 5. 数据表达与效率问题

- 时间线是实体当前快照的拼接：每个 Idea 只一条 updated_at、每个 Run 一条 created_at，没有完整展示版本演进、证据判断、AI 应用等过程；固定截断 80 条且无加载更多。见 `timeline-view.tsx` 的 mergeEvents。
- 图谱所有历史版本都采用 Idea 的当前状态（`backend/app/services.py`），容易被理解为历史版本当时的状态。需要明确“当前假设状态”与“版本当时判断”的区别。
- 实验台把第一个指标称为主指标、仅展示第一条关联假设；缺少明确的主指标设置。指标展示应有名称、单位和优化方向。
- 实验对比把每条曲线单独归一化，横轴按数据点序号而非真实 step（`metric-chart.tsx:19`）；形状相近不代表量级或收敛速度相近。应统一坐标或清晰显示各自量程。
- 实验选择逐项限制 4 个，全选却不限制；比较页直接 slice(0,4)，造成“选择数量”与实际展示不一致。
- 实验台加载 N 个实验需要 2 + 2N 个请求，并获取指标序列；任一详情失败会使整批 rows 无法更新。数据增长后会明显影响等待和恢复。
- 总览活跃假设计数直接使用截断到 4 条后的数组长度；研究焦点来自假设时却标为“来自项目描述”。
- 多个模块把请求失败降级为空数组或无待办，用户无法区分“没有内容”和“没有加载成功”；项目列表的 refresh 则缺少可供首页展示的错误状态。
- 表单和页面状态大多仅存在组件内存中，导入文本等长内容缺少离开提醒或草稿恢复；连续操作的上下文保留不足。
- 设置页告诉用户在 backend/.env 配置 GLM，但没有应用内配置与检测入口；桌面更新桥接已提供接口，设置页没有调用检查更新和下载通知接口。面向桌面用户的功能入口尚未完成。
- README 中的阶段说明、测试数量、GLM 范围与后续实现不一致，需要在实现稳定后同步。

## 6. 建议的产品主线

建议将工作围绕研究问题组织，保留专业数据结构，但减少用户必须理解的内部术语。

1. **记录材料**：随手记、研究讨论、实验结果统一有入口，原始内容可保留。
2. **整理认识**：AI 将材料整理为假设、证据候选、待解问题和建议修改；用户在明确的目标对象上确认。
3. **推进验证**：在假设详情直接安排实验，实验计划关联验证目标；结果产生后再建立证据判断。
4. **记录决策**：明确说明支持、反驳或仍不确定，记录为什么修订、继续或搁置。
5. **继续研究**：项目工作台展示真实未完成事项和最近上下文，图谱、时间线作为观察同一研究过程的视图。

不必立即引入完整任务管理系统，但需要明确区分开放问题、实验计划、证据判断、研究决策的含义。仅靠笔记标题前缀不能承载长期状态管理。

建议页面组织：项目工作台 → 研究问题/假设 → 实验 → 材料与笔记；待审数量作为明确队列入口；图谱和时间线放在项目研究过程的视图切换中。对话导入与结构化导入可以保留两种方式，但应共享“导入材料—预览整理—确认结果”的体验。

## 7. 实施顺序与验收

第一轮：修复路由、ID 对应、项目上下文、预览一致性和历史待审恢复。验收覆盖两个项目、同一会话多次分析、刷新恢复、旧任务待审、预览后改内容、桌面内部跳转与直接打开。

第二轮：补齐“假设 → 实验计划 → 结果 → 证据 → 修订”的常规操作；支持编辑状态、维护笔记、查看并处理开放问题。用户应能只用界面完成闭环，无需 API 或外部 JSON 操作。

第三轮：统一项目工作台与旧项目页，减少入口重复；再调整图谱默认层级、时间线事件表达、指标比较和加载策略。

视觉调整放在主流程明确之后，避免将时间投入到仍会被重组的页面布局中。
